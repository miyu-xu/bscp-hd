# HD 与 AOSP Cuttlefish Android 功能对齐

## 基线与判定

本矩阵以 `device/google/cuttlefish` 的 `android-platform-15.0.0_r14` 标签为产品基线。审计时该标签解析到提交 `c8b2053b7b8e21904d5437bbd9c3d0d1f7cd9806`。主要事实来源为：

- [Android 15 Cuttlefish WebRTC 控制面](https://android.googlesource.com/device/google/cuttlefish/+/refs/tags/android-platform-15.0.0_r14/host/frontend/webrtc/html_client/client.html)
- [Android 15 动态显示命令](https://android.googlesource.com/device/google/cuttlefish/+/refs/tags/android-platform-15.0.0_r14/host/commands/display/main.cpp)
- [Android 15 vsock 相机 Guest HAL](https://android.googlesource.com/device/google/cuttlefish/+/refs/tags/android-platform-15.0.0_r14/guest/hals/camera/)
- [AOSP Cuttlefish 环境控制](https://source.android.com/docs/devices/cuttlefish/control-environment)
- [AOSP Cuttlefish Bluetooth 控制](https://source.android.com/docs/devices/cuttlefish/bluetooth)
- [AOSP Cuttlefish 控制面与自定义动作](https://source.android.com/docs/devices/cuttlefish/control-panel)

“对齐”表示用户能完成同类测试目标，不要求复制 WebRTC 架构。HD 是本机零拷贝桌面产品：WebRTC 视频编码、浏览器内 ADB 和任意 shell 自定义按钮不进入产品路径。每项证据严格区分：

- `verified`：Windows 和 macOS 的真实 Android 15 Guest 都已回读；
- `implemented`：portable contract、运行时和 UI 已实现，但本轮双端真机证据不完整；
- `partial`：只覆盖 AOSP 能力子集；
- `blocked`：缺少实现、制品或外部条件；
- `non-goal`：被产品架构或安全边界明确替代。

## 实施顺序

1. P0：完成已有控制能力的按实例 UI、参数边界和 Windows/macOS 真实 Guest 回读。
2. P1-A：路线导入、屏幕录制、UWB 距离、modem 状态、BLE Beacon/受限广播序列、HOGP 键盘与有界 HCI btsnoop 已实现；Windows modem、活跃 FiRa、路线 framework 回调、录屏与 Guest 虚拟相机真实 Guest 门已关闭，继续完成 macOS 新 FiRa/路线分发门。legacy keyboard/loopback 不恢复，PHY/remote console 继续阻断。
3. P1-B：完整 bugreport、冷启动多显示器与按显示录屏已实现；运行时显示热插拔保持发布阻断，继续 Host 麦克风/相机注入。
4. P2：Wi-Fi 环境、持久 snapshot 和经过显式授权的 powerwash。

所有新增能力先进入 `hd-core` 的 portable contract，再进入平台 adapter、Worker/Host、UI 和黑盒 smoke。日常显示必须继续证明 gfxstream 硬件路径、平台原生外部资源、显式同步、零 CPU readback/software blit，并明确 `SwiftShader=false`；只有用户显式开始录屏后的录制支路允许有界非零拷贝读回，且停止录屏必须立即注销，不得演变成显示回退。
